### 2026-08-16 NES.emu 스테이지 5 이후 글자 깨짐 제보 — 헤더 원인 아님(검토만)

- 제보 증상: Android `NES.emu`에서 5스테이지 종료 뒤 다크 퀸/브리핑 화면의 한글이
  무작위 글리프로 바뀌고 다음 진행이 멎는다는 스크린샷을 받음. 이번 작업은 원인 검토만
  수행했으며 ROM·빌드 스크립트·배포물은 수정하지 않았다.
- 현재 개발 ROM 헤더(16바이트):
  `4E 45 53 1A 20 00 70 00 00 00 00 00 00 00 00 00`.
  `PRG=32×16KiB=512KiB`, `CHR-ROM=0`(CHR-RAM 사용), `mapper=7`, trainer/battery 없음으로
  빌드 구조와 일치한다. 원본은 같은 mapper 7에 `PRG=16×16KiB=256KiB`이다.
- 이 프로젝트는 AxROM의 비표준 512KiB 확장으로 레지스터 bit 3을 네 번째 PRG 뱅크
  비트로 사용한다. NESdev도 이 방식을 일부 에뮬레이터가 지원하며 512KiB Battletoads
  ROM hack 사용 사례가 있다고 기록한다. 따라서 다른 에뮬레이터/실기 호환성 위험은
  존재하지만, 헤더의 PRG 크기 바이트를 임의로 바꾸는 것으로 해결할 문제는 아니다.
- 최신 NES.emu 공식 소스의 FCEU 코어는 mapper 7 동기화에서
  `setprg32(0x8000, latche & 0xF)`를 사용한다. 저장소의 2012년 초기 이력까지 같은
  4비트 선택이므로 NES.emu가 bit 3을 무조건 버린다는 가설도 현재 근거와 맞지 않는다.
- 스크린샷의 국소적인 글리프 혼선은 헤더 전체 오인식보다는 한글 글리프 목록/CHR-RAM
  상태 불일치 쪽에 가깝다. 특히 직전에 확인한 엔딩 ID 117~119 목록 범위 초과와 초상화
  타일을 침범한 48슬롯 초과 결함은 같은 계열의 화면 붕괴를 만들 수 있다. 다만 해당 두
  결함은 각각 14스테이지 엔딩 경로로 확인됐으므로, 이번 5스테이지 제보와 동일 원인이라고
  단정하지 않는다.
- 확정에 필요한 제보 정보: 실제 실행 ROM SHA-256, NES.emu 정확한 버전/배포처,
  새 게임으로 연속 플레이했는지 또는 자동 재개·세이브 스테이트를 사용했는지, 최신 ROM에서
  기존 상태를 불러왔는지. ROM 교체 뒤 구버전 자동 상태를 복원하면 RAM/CHR-RAM·코드가
  서로 다른 빌드에 속할 수 있으므로 반드시 새 게임/콜드 부팅 재현과 분리해야 한다.
- 다음 검증 순서: 제보 ROM 해시를 배포 manifest와 대조 → NES.emu에서 자동 상태 삭제 후
  1~6스테이지 연속 재현 → 같은 ROM/진행 상태를 Mesen·BizHawk와 비교 → 최초로 깨지는
  화면 ID, `$BD/$CE`, 글리프 목록 pointer/count, CHR `$C5~$FF`를 기록한다.
- 참고: 검토 시점의 작업 트리는 다른 엔딩 문안/빌드 갱신 중이어서 개발 ROM 해시가
  문서에 적힌 이전 배포 해시와 달랐다. 이번 제보 판정에는 그 중간 개발 ROM을 배포본으로
  간주하지 않았다.
